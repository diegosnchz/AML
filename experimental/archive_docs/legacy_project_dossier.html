Todo el proyecto, sin marketing

AMLGuardian no es una app de negocio tradicional. Es una plataforma de monitorizacion AML montada sobre Docker que ingesta CSVs de IBM AML, los normaliza en PostgreSQL, modela features con dbt, genera alertas por tipologia, proyecta la red en Neo4j y asigna un score de riesgo con XGBoost.

Resumen ejecutivo

Que resuelve cada capa

La plataforma esta pensada para dejar al analista con un problema ya reducido: cuentas, alertas, relaciones y narrativas de riesgo. La infraestructura, el modelado y la priorizacion quedan automatizados.

1. Ingesta

Limpia y aterriza CSVs

scripts/ingest.py normaliza cabeceras, convierte importes a EUR con un mapa FX simple, elimina filas invalidas, deduplica y recrea raw.transactions y raw.accounts.

chunk_size = 100_000 | indices sobre id y timestamp
2. Transformacion

dbt fabrica staging, features y alertas

dbt deduplica la capa staging, calcula una fila de comportamiento por cuenta en features.fct_account_features y consolida las tipologias AML en alerts.fct_alerts.

staging -> marts.features -> marts.alerts
3. Red

Neo4j detecta estructura de relaciones

scripts/load_graph.py proyecta la red de cuentas en Neo4j, calcula PageRank y Louvain y vuelca el resultado de nuevo a PostgreSQL para unificar la investigacion.

ml.graph_account_metrics
4. Scoring

XGBoost prioriza el riesgo

scripts/train_model.py compara 3 enfoques, entrena el modelo principal con SMOTE, genera SHAP y escribe scores 0-100 y tiers de riesgo para cada cuenta.

LOW / MEDIUM / HIGH / CRITICAL

Explorador de capas

Lo que hace scripts/ingest.py

  • Normaliza nombres de columna usando regex.
  • Convierte amount_original a numerico y calcula amount_eur.
  • Usa un mapa FX fijo para EUR, USD, GBP y CHF.
  • Elimina filas sin ids, timestamp o importes validos.
  • Deduplica por transaction_id y account_id.

Housekeeping posterior

  • Borra duplicados residuales en raw usando ctid.
  • Crea indices sobre ids y combinaciones cuenta + timestamp.
  • Carga transacciones en chunks de 100_000 filas.
  • Registra recuentos acumulados y errores de fuente faltante.

Lo que hace dbt

  • Deduplicacion logica de staging con distinct on.
  • Feature engineering por cuenta para scoring.
  • Reglas AML como modelos SQL legibles y testeables.
  • Tabla union fct_alerts y agregacion fct_sar_candidates.

Calidad de datos

  • Tests de esquema en schema.yml para not_null, unique, relationships y accepted_values.
  • Tests SQL custom para importes positivos, ratios validos y umbral SAR.
  • dbt docs generate se ejecuta al final del bloque dbt.

Tablas para analista

  • alerts.fct_alerts: un registro por alerta disparada.
  • alerts.fct_sar_candidates: cuentas con 3 o mas alertas o alguna critica.
  • ml.risk_scores: score, tier y top 3 features explicativas.
  • ml.graph_account_metrics: PageRank y comunidad Louvain.

Queries de soporte

  • sql/investigations/smurfing_deep_dive.sql
  • sql/investigations/circular_flows.sql
  • sql/investigations/high_risk_accounts.sql

Feature mart

Campos que alimentan el modelo y la investigacion

features.fct_account_features mezcla vista emisor y receptor para construir comportamiento por cuenta. El campo velocity_7d se calcula respecto al maximo timestamp del dataset, no respecto al reloj del servidor.

  • total_sentTotal enviado en EUR.
  • total_receivedTotal recibido en EUR.
  • n_transactionsConteo combinado de envios y recepciones.
  • avg_amount_sentMedia de importes salientes.
  • stddev_amount_sentVolatilidad de importes salientes.
  • n_unique_counterpartsNumero de contrapartes distintas.
  • n_countries_transactedPaises distintos de contrapartes.
  • ratio_night_transactionsPorcentaje entre 00:00 y 06:00 UTC.
  • max_single_transactionMayor importe individual.
  • velocity_7dEUR enviado en la ventana final de 7 dias del dataset.
  • is_laundering_anyTarget sintetico de validacion, no variable de negocio.
Motor de deteccion

Las seis reglas AML implementadas

Las reglas estan codificadas como modelos dbt. Cada una genera un alert_id determinista, una severidad y una descripcion lista para el analista. Despues se consolidan en alerts.fct_alerts.

Smurfing

72h rolling

Busca pagos salientes por debajo de EUR 9,999 acumulados en una ventana movil de 72 horas por cuenta emisora.

  • Entrada: solo transacciones con amount_eur < 9999.
  • Disparo base: 5 o mas operaciones en 72 horas.
  • Severidad: MEDIUM desde 5, HIGH desde 10, CRITICAL desde 15.
  • Conserva la mejor ventana por cuenta segun volumen y conteo.
dbt/models/marts/alerts/alert_smurfing.sql

Fan-out

24h dispersion

Detecta cuentas que distribuyen fondos a muchos beneficiarios distintos en solo 24 horas.

  • Cuenta por emisor usando ventanas ancladas por transaccion.
  • Disparo base: 10 receptores unicos en 24h.
  • HIGH a partir de 15, CRITICAL a partir de 20 receptores.
  • Descripcion lista para justificar patron de dispersion.
dbt/models/marts/alerts/alert_fan_out.sql

Fan-in

24h aggregation

Es el inverso operativo del fan-out: una cuenta receptora que agrega fondos de muchos originadores distintos.

  • Se agrupa por cuenta receptora.
  • Disparo base: 10 emisores unicos en 24h.
  • HIGH desde 15, CRITICAL desde 20.
  • Se describe como nodo de consolidacion o mule collection node.
dbt/models/marts/alerts/alert_fan_in.sql

Circular

7 day loop

Usa un CTE recursivo para encontrar ciclos de exactamente 3 saltos donde los fondos vuelven al origen en menos de 7 dias.

  • Ruta tipo A - B - C - A.
  • Lookback configurable por variable dbt, 90 dias por defecto.
  • MEDIUM si el ciclo existe, HIGH desde EUR 50k, CRITICAL desde EUR 100k.
  • Solo se conserva el ciclo de mayor importe por cuenta raiz.
dbt/models/marts/alerts/alert_circular.sql

Layering

Step-down chain

Busca cadenas secuenciales donde cada transferencia mueve entre el 85% y el 99% del importe previo, dejando una comision aparente.

  • Hop maximo: 48h entre un salto y el siguiente.
  • Profundidad minima: 3 saltos.
  • HIGH si la cadena llega a profundidad 4, CRITICAL si llega a 5.
  • Evita repetir cuentas en el camino para no contaminar la cadena.
dbt/models/marts/alerts/alert_layering.sql

High-risk geography

Watchlist exposure

Marca cuentas expuestas a una watchlist hardcodeada de 15 jurisdicciones de riesgo o monitorizadas.

  • Evalua pais del emisor y del receptor.
  • Severidad por numero de exposiciones: MEDIUM, HIGH desde 5, CRITICAL desde 10.
  • Lista actual en SQL, no externalizada.
  • Incluye paises como IRAN, DPRK, MYANMAR, NIGERIA y VENEZUELA.
dbt/models/marts/alerts/alert_high_risk_geography.sql
Red y scoring

Como combina Neo4j con el modelo

El proyecto no se queda en reglas. Construye una red dirigida de cuentas y usa el mart de features para un scoring supervisado. La explicabilidad queda materializada en SHAP y los resultados vuelven a PostgreSQL para consulta unificada.

Capa de grafo

Que escribe y calcula Neo4j

scripts/load_graph.py limpia el grafo, crea un constraint unico para Account.id, vuelca cuentas y transferencias desde staging y proyecta amlguardian_graph para correr algoritmos GDS.

Nodos Account

Propiedades: id, name, country, account_type, risk_score.

Relaciones TRANSFERRED

Propiedades: transaction_id, amount_eur, currency, timestamp, is_laundering.

Metricas PageRank + Louvain

Se persisten en ml.graph_account_metrics con account_id, pagerank_score, community_id.

PageRank

Sirve para destacar cuentas influyentes dentro del flujo transaccional. El script ordena y loggea el top 20 tras cada refresco.

Louvain

Agrupa comunidades de cuentas densamente conectadas, util para rings, clusters de mulas o hubs de agregacion.

Capa ML

Como puntua el riesgo

scripts/train_model.py carga el mart de features, hace train_test_split(test_size=0.25, stratify=target), corrige desbalance con SMOTE y compara tres enfoques.

Benchmarks

  • XGBoost con 300 estimadores, max_depth=5 y learning_rate=0.05.
  • LightGBM con 300 estimadores y num_leaves=31.
  • Isolation Forest con contaminacion alineada a la proporcion positiva del train.

Output final

  • El modelo principal es XGBoost.
  • Genera probabilidades, score 0-100 y risk_tier.
  • Guarda top 3 features por cuenta usando SHAP.
  • Escribe resultados tanto a CSV/JSON/PNG como a ml.risk_scores.

Rangos de tier

  • LOW: menos de 25
  • MEDIUM: 25 a 49.99
  • HIGH: 50 a 74.99
  • CRITICAL: 75 o mas

Artefactos

  • outputs/risk_scores.csv
  • outputs/model_metrics.json
  • outputs/shap_summary.png
Salida para investigacion

Tres casos que explican la utilidad final

Estos casos estan documentados en el README del repo y muestran como convergen reglas, score ML y contexto de red para construir una narrativa de investigacion razonable.

Hallazgos

  • 17 pagos por debajo de EUR 9,999 entre 2022-11-04 y 2022-11-07.
  • Ratio nocturno 0.71 frente a media de dataset 0.12.
  • Score ML 91.4 con drivers velocity_7d y n_unique_counterparts.
  • PageRank 0.0041 y fuerte cluster en la misma comunidad Louvain.

Porque importa

La secuencia es el patron de structuring mas recognoscible del repo: entrada grande, dispersion inmediata y fuerte actividad nocturna. El proyecto demuestra que no depende solo de una regla; cruza rule engine, ML y network context.

Hallazgos

  • 13 transferencias entrantes con total de EUR 134,600.
  • Salida unica posterior de EUR 131,200 con retencion del 2.5%.
  • Score 88.7 / HIGH con peso en geografias y actividad nocturna.
  • Top 0.3% por centralidad de intermediacion segun narrativa README.

Porque importa

Ensena que el proyecto no solo ve volumen, sino exposicion geografica y comportamiento de hub. La recomendacion final ya apunta a EDD, SAR y KYC refresh.

Hallazgos

  • Ciclo cerrado en 5 dias con total reciclado de EUR 179,830.
  • Importes retenidos del 97.0% al 97.2% en cada hop.
  • Layering se dispara antes de cerrarse el retorno circular.
  • Scores 94.1, 87.3 y 82.6 para las tres cuentas involucradas.

Porque importa

Es la mejor prueba del valor combinado del proyecto: SQL recursivo para el patron, clustering de red para el contexto y scoring para priorizar la investigacion.

Runbook

Como se levanta y como se usa

Este proyecto esta pensado para correr localmente con Docker Compose. Lo minimo es configurar secretos en .env, dejar los CSV en data y arrancar el stack.

1

Preparar entorno

Copia .env.example a .env y cambia todos los CHANGE_ME_*.

  • Postgres, Airflow y Neo4j leen secretos desde variables de entorno.
2

Cargar datos

Coloca transactions.csv y accounts.csv en data/.

  • La ingesta falla si no encuentra los ficheros.
  • Las rutas se leen desde TRANSACTIONS_CSV y ACCOUNTS_CSV.
3

Arrancar stack

Ejecuta docker compose up -d en la raiz del repo.

  • Se construyen servicios Airflow y se levantan Postgres, pgAdmin y Neo4j.
  • airflow-init migra base y crea el usuario admin.
4

Operar pipeline

Abre Airflow y dispara amlguardian_pipeline para la primera carga, o espera a la planificacion diaria.

  • Airflow: localhost:8080
  • pgAdmin: localhost:5050
  • Neo4j Browser: localhost:7474
Limitaciones y extensiones

Lo que esta bien y lo que todavia es portfolio

El proyecto ya refleja una arquitectura realista, pero sigue siendo un portfolio. Hay varias piezas que conviene endurecer si la idea es acercarlo a una implementacion mas productiva.

Limitaciones actuales

  • Mapa FX hardcodeado y corto, definido dentro de scripts/ingest.py.
  • Lista de geografias de riesgo hardcodeada en SQL.
  • El scoring usa el label sintetico is_laundering_any, no feedback humano real.
  • No hay una API ni una UI transaccional propia; las interfaces son herramientas operativas de terceros.

Siguientes pasos razonables

  • Externalizar FX y watchlists a tablas seed o feeds versionados.
  • Incorporar feedback loop del analista para retrain con SAR confirmados.
  • Aniadir metricas de grafo adicionales: weakly connected components, betweenness o shortest path.
  • Montar una capa web operativa propia si quieres un frontend real para usuarios internos.
Cierre

La idea central del proyecto

AMLGuardian automatiza la parte pesada de un stack de monitorizacion AML: ingestar, transformar, detectar, contextualizar y priorizar. Lo que queda para el analista es la parte de criterio: investigar, redactar narrativa y decidir escalado.
